feat(knowledge): add immutable versions and authorized publication history

I established the knowledge data and authorization foundation before retrieval or AI. I separated logical article identity from immutable version UUIDs and retained the existing support/management scope boundary: requesters cannot access knowledge, agents read authorized published support content, and managers manage the lifecycle.

Important changes and reasons:
- I added the 0004 migration with article publication pointers/revisions, immutable snapshots containing normalized content/provenance/hashes, and FK-backed knowledge events. Composite constraints prevent cross-article pointers; PostgreSQL triggers reject UPDATE/DELETE/TRUNCATE of snapshots and audit history. A single publication pointer replaces the earlier planned partial published-status index without rewriting old content.
- I added manager-only draft/publication/archive operations with current actor checks, article row locking, strict expected revisions and the existing persistent idempotency mechanism under separate knowledge operation names. Business/version/audit/idempotency changes commit together, and failed audit writes roll back everything.
- I made historical reads recheck current article availability and both historical/current scopes. Publishing management-only content or archiving denies old support references to agents. Historically readable versions are distinct from current retrieval candidates. An old successful publication retry returns its receipt without restoring old state.
- I kept ticket audit constraints and the existing audit endpoint intact, adding explicit knowledge history instead of a weak polymorphic resource FK. Lists use bounded identity/role/query/article-bound signed cursors; agent article views omit draft revision metadata.
- I added four original English synthetic fixtures, required source/license notes and a repeatable draft-first importer. References are literal data, not fetched URLs or a claim of verified external licensing. Repeat imports do not overwrite history or unarchive content.
- I added PostgreSQL tests for immutability, cross-article constraints, scope/history isolation, idempotency, rollback, migrations, seeding and independent-connection concurrency, plus a real HTTP publication/history scenario in both existing Playwright projects.

Validation: final backend 226 tests passed with zero skips;17 API,11 query/mutation,6 write and12 component tests passed; clean npm installation, test-source types and production build passed. All12 E2E cases passed in17.8 seconds, including the existing ticket regression. The actual development database upgraded0003 to0004 while preserving original rows/counts in all six existing tables, then imported four unpublished synthetic drafts twice without duplication; readiness passed. The initial TRUNCATE test was corrected to reach the trigger after FK preflight, and the execution record preserves that failed assertion. Exact commands, limits and cleanup are documented in docs/evidence/2026-10-27-knowledge-versioning.md.

Limitations: no knowledge management UI, keyword/vector retrieval, model execution, AI citations, cloud deployment or verified remote CI. Immutable DML guards do not resist privileged schema administration. The synthetic corpus has four examples, not the planned 20-30 articles or completed evaluation labels. Historical evidence/data is preserved. Next: S14 authorized retrieval and persistent vector representation with measured model/license decisions.

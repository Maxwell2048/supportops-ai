feat(mcp): add a read-only MCP server that reuses the API's authorization

I added a Model Context Protocol server so external MCP clients such as Claude Code or Claude Desktop can read support data, while the server keeps every decision. The client and its model only propose tool calls; this server decides with the same token, role and object rules as the REST API.

I built it on the official MCP Python SDK, pinned as mcp==2.3.0 with uv add, which updated uv.lock. I used the low-level Server with explicit tools/list and tools/call handlers instead of the decorator-based MCPServer, because I need exact control over input schemas, the order of checks and error text. The server runs as its own process from the create_mcp_app factory, with stateless Streamable HTTP and JSON responses at /mcp and loopback-only Host and Origin checks. I kept it separate from the FastAPI app so it can stay off by default, owns its own lifespan and transport security, and cannot change REST behavior; reuse happens by calling the same functions, not the REST API.

Authentication reuses the access JWT: an SDK TokenVerifier calls the API's decode_subject, so issuer, audience, expiry and required claims are checked exactly as in the API, and invalid tokens get HTTP 401 before JSON-RPC parsing. Only the subject and a digest of the token are kept; the token is never stored, logged or forwarded, and no tool calls another service. Every tool call then runs in its own short transaction that reloads the user. Unknown and inactive users get invalid_session and requesters get forbidden before the tool name or arguments are examined, so deactivation, a role change or a reassignment applies on the next call.

The four tools are list_my_tickets, get_ticket, ticket_history and search_knowledge. Each has a strict Pydantic model with forbidden extra fields, no type coercion and bounded limits; rejections report field names and error types only, and an unknown field is reported as <extra>, so neither values nor client-chosen key names are echoed. Reads go through list_tickets, visible_ticket, the analysis tool's own _history function and the scoped keyword retrieval.search. A ticket outside the caller's scope returns the API's own not_found code and message, identical to a nonexistent ticket. Results omit internal notes, author IDs, requester identity, email and phone. Ticket and knowledge text appears only in structured result fields, and the fixed tool descriptions say it is untrusted content.

The existing audit_events table only accepts successful ticket writes, so I added migration 0011_mcp_tool_calls. Each call writes one row in its own transaction with the request ID, actor and role snapshot, tool or "unknown", outcome, requested ticket ID, returned object IDs and a count, and never argument values. A result is returned only after that transaction commits. I added the table to the Compose restore fingerprint list and moved the readiness schema revision to 0011.

Validation: I started the existing local PostgreSQL 17.11 container with the repository helper and ran the backend suite through scripts/test_backend.py: 421 passed with zero skips. That includes 32 new unit tests and 8 new PostgreSQL integration tests that drive the SDK client over Streamable HTTP, and also the LangGraph tool-loop integration cases that had not executed before. Without a database, cd backend; uv run pytest gave 145 passed and 276 skipped, all for the missing TEST_DATABASE_URL. A separate uvicorn process with a throwaway secret and no database returned 401 without a token, 421 for a foreign Host header and listed the four tools over a real socket. The repository language check passed.

Limitations: I did not connect a real Claude client, did not migrate the development database to 0011, did not run the Compose restore check and did not run remote CI. Tokens must be replaced by hand when they expire. Remote exposure would need TLS, OAuth 2.1 and rate limiting. There are no write tools; ADR 0012 records what one would need (an idempotency key, a draft-only effect and human confirmation in the review workspace).

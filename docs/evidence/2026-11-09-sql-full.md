# Full-row synthetic ticket query observation

On 2026-11-09, PostgreSQL 17.11 ran the application ticket model's full-row projection, assignee and status filters, and descending timestamp/ID page order in an isolated migrated schema. The fixture contained 5,000 deterministic synthetic tickets in addition to the fixture records. The script only drops and recreates `ix_tickets_assignee_status` after verifying that the current schema is its generated disposable test schema. The schema is removed after execution. No application index is changed.

From backend, run `uv run --locked python ../scripts/experiment_ticket_full.py`. Five EXPLAIN ANALYZE executions per configuration returned the same 21 IDs. Without the index, the observed plan used a sequential scan and top-N sort. With the existing composite index, PostgreSQL used a backward index scan. Median execution times were 0.207 ms and 0.018 ms respectively in this run.

Five 1,000-row bulk inserts were timed within savepoints and rolled back for each configuration. Median client-observed insert times were 9.899 ms without the index and 11.386 ms with it. These include local client and database execution but not transaction commit. The runs were sequential, used warm caches and a single fixed distribution, and do not establish general throughput or production performance. Concurrent traffic, other filters, cold caches, durability costs and larger datasets remain unmeasured.
